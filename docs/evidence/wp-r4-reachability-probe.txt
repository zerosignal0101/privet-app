================================================================================
1. The defect and the change
================================================================================

Root cause (as diagnosed): `lib/pages/home_page.dart` judged a Known Devices row
with a single `online` boolean, taken from `onlinePeerFingerprintsProvider`
(lib/providers/peers.dart), which only reads `isOnline` off the *discovery*
peer list. `TrustedPeerDto.addresses` — the address the engine records after a
successful send — was not part of the judgement at all. So a device that was
trusted, had a remembered address, and had just received a file stayed greyed
"Offline" with no Send button, and no amount of refreshing could change it.

Fix, in four states by priority (lib/providers/peers.dart, ReachabilityNotifier):

  1. online      — currently broadcasting (discovery). Unchanged behaviour,
                   green. No probe is issued for these at all.
  2. reachable   — not broadcasting, but `resolve_address` on
                   `addresses.first` answered AND answered with a fingerprint
                   byte-for-byte equal to the row's own fingerprint.
                   Copy: "Reachable at <ip>", address shown, Send offered.
  3. unreachable — probed, and it did not yield *this* device: nobody answered
                   (`found: false`), the probe failed/timed out, or something
                   answered under a different identity.
                   Copy: "No answer at <ip>", address still shown, no Send.
  4. unknown     — no remembered address to probe, and not broadcasting.
                   Copy: "Offline".

The fingerprint comparison is the safety property, not a detail. A remembered IP
can be reassigned by DHCP to a different machine; "something answered at the
address I remember" must never be rendered as "my friend is there", because that
renders a Send button that delivers files to a stranger. So a mismatch is
treated exactly like no answer, and the copy deliberately does not distinguish
the two cases (naming the stranger would also leak what is at the address).

The row now always shows the remembered address (IPv6 bracketed via
`isIpv6Literal`), in every state, so "we tried it and nothing answered" is
actionable — the user can see which address was tried.

Sending: for a reachable-but-not-broadcasting device the Send button hands the
probed address to the send page as `via` (SendPreparationPage.initialViaIp).
Without that the send would have no way to resolve the device and would fail
even though the row says it is reachable. For a broadcasting device `via` stays
null, so discovery is used as before.

Cost / triggering:
  - Probing runs only inside `_refresh()` (pull-down and the desktop AppBar
    button). No timer, no polling, no background work.
  - Only trusted devices that are not currently broadcasting and do have an
    address are probed; exactly one address each (`addresses.first`); once per
    refresh.
  - Probes run concurrently via `Future.wait`, so N unresponsive devices cost
    one timeout, not N.
  - Bounded at kReachabilityProbeTimeout (5 s) per address.
  - Rows under probe show a spinner and "Checking <ip>…"; because the probes
    are awaited inside `_refresh`, the pull-down indicator stays up until they
    finish.

  c. "an address where nobody answers shows no answer and keeps the address

      `found: false`. Asserts "No answer at 10.29.218.79", the address remains on

      Cost control. The device is in the `list_peers` snapshot, so after a full

      settles on "No answer at 10.29.218.79", keeps the address, offers no
      Send, and that the refresh indicator is gone.

================================================================================
3. Supporting change: the probe bound had to move into the IPC request
================================================================================

The first implementation wrapped the probe in an outer `.timeout()`. That passed
the UI assertions but left the IPC client's own 30 s request timer pending,
which flutter_test correctly rejects ("A Timer is still pending even after the
widget tree was disposed"). That is not only a test artifact: an outer timeout
means the app moves on while a 30 s timer is still running and a late reply can
resolve an abandoned completer, so a refresh would still pin a timer for far
longer than the refresh it belongs to.

So the bound is now passed to the request itself: `callRaw` takes an optional
per-call timeout override (defaulting to the client-wide 30 s, so every other
caller is unaffected), `resolveAddress` on the client and on `PrivetService`
forward it, and the probe passes `kReachabilityProbeTimeout`. On timeout the
pending entry is removed, so neither the map nor an abandoned completer grows
per timed-out probe. Net: the client-level bound becomes the real bound.

No third-party dependency was added. `android/`, `tool/` and `pubspec.yaml` were
not touched; `analysis_options.yaml` and `pubspec.lock`, which the flutter
commands rewrite, were restored with `git checkout --` before committing.
